## 1. 先说三处与设计文档的假设不一致的地方

1. **参考实现没有直接依赖 mini-swe-agent。** 它的 `ClmAgent` 是为 Harbor 框架写的（`harbor.agents.base.BaseAgent` + litellm），只是沿用了 mini-swe-agent 的做法：单个 bash 工具、THOUGHT 加一条命令的系统提示。本项目继续用 mini-swe-agent 的 `DefaultAgent` 做底座（v0.2 的 `BudgetedAgent` 已经这样做），参考实现的机制移植到 `query` / `execute_actions` 这两个覆盖点上，不引入 Harbor。
2. **子智能体"新建 / 删除上下文文件"的实现不在公开代码里。** `harness.py` 把 `subagents`、`n_subagent_slots`、`subagent_max_steps`、`subagent_lifetime_cap` 等参数列在 `_REMOVED_KWARGS`（"不属于本次发布的实验功能"），传入会直接报错。公开代码里只剩痕迹：`context_env/env.py` 里的路径名 `SUBCTX`、`subagents`、`finished_subagents`，以及轨迹格式里的 `subtrajectories`（子智能体轨迹挂在父轨迹上，带启动与折叠两个链接）。所以子智能体的启动、结束、额度、计数，本项目要自己写；能借鉴的只有"子智能体有自己的上下文、结束后结果折叠回父上下文、轨迹挂在父轨迹下"这个组织方式。
3. **公开代码里没有"四部分"结构的 skill 样例。** 仓库里没有任何 `SKILL.md`；提议者提示只规定了输出格式：YAML 头部（`name`、`description`）加一段编号规则正文。设计文档第 4.3 节的四部分正文（机制、怎么做、怎么用读数、怎么确认做对了）按文档自己的定义实现，无法与论文原文逐条核对。

| 管理动作不计步数（§3.3） | `harness.py` `ctx_turn_is_free`：纯压缩的一轮不消耗任务步数；另有 `lm_call_cap` 限制总调用数，防止免费轮无限循环 | 采用：更新记忆文件、压缩、申请追加、调用子智能体不计入步数上限，token 照常记账；另设总调用数上限 |
| 子智能体（§2.2） | 公开代码里没有实现（见第 1 节第 2 点） | 新写 `subagents.py`：执行者用一条特殊命令调用，参数是类型、任务说明、token 额度；程序检查次数上限和可批上限，从账本扣出额度，子智能体在同一工作区运行，执行者暂停，结束后退回余额，把结果作为这条命令的输出 |

## 3. 参考机制中不采用的部分及原因

| 参考机制 | 不采用的原因 |
|---|---|
| 模型直接编辑上下文镜像文件来压缩 | 一是它把镜像放在沙盒内的 `/tmp`，本项目的沙盒禁止智能体读写全局 `/tmp`，要用就得改沙盒可读写路径，按规定不放宽。二是设计文档 §2.3、§4.2 规定的是"记忆文件 + 程序压缩"，压缩时机和保留内容由 skill 决定，这才是要进化的对象 |
| Harbor 框架、Harbor 的沙盒与评分 | 本项目有自己的沙盒（Landlock + 网络拦截）和密封评分，不能替换 |
| FLOPs 计量、后缀缓存复用、`clm_rl`、ContextBench | 与本设计无关；设计文档 §1 第 4 条也规定不引入它的数据集、权重和评分器 |
| 上下文预算极小（约 3 万 token）下的参数默认值 | 本项目的窗口沿用 v0.2 的 20 万，阈值由 skill 给出 |
| 提议者读命令与输出原文 | 违反 §6.2"不看任何代码、测试内容或 held out 用例信息" |
| 候选只和单一现任比、通过后替换 | 设计规定两层帕累托前沿 |

## 6. 需要用户决定的事项

1. **审阅者"只读"怎么保证。** 两种办法：(a) 给审阅者一个只读的沙盒策略，工作区对它不可写；这等于新增一种沙盒策略，按规定要先得到同意。(b) 沙盒不动，审阅者结束后由程序用 git 检查工作区，有改动就全部撤销并记录。建议 (a)，更可靠；它是收紧而不是放宽。
2. **pathspec 和 fsutil 的阶段计划。** 本项目只有 deepdiff 的冻结计划。AdaMAS-single 的 `configs/datasets/rsi_pilot_plans/` 里有这两道题的计划（各 4 个里程碑，格式与 deepdiff 的一致）。建议只读复制过来并冻结，不改动 AdaMAS-single。
3. **没有出题者之后的"本阶段完成"。** 执行者声明完成即进入下一阶段，程序不设验收门，只记录当时的导入检查缺失数和它自己测试的通过数。这是按 §2.1 的字面实现；如果希望声明完成时加一个最低条件（例如包能导入），请说明。
4. **规划者与进化者用哪个模型。** v0.2 都用 gpt-5.6-luna（与执行者相同）。参考实现允许提议者用更强的模型。建议先保持相同，记为"自我进化"。
5. **上下文窗口取值。** 沿用 v0.2 的 20 万 token，还是为了让上下文管理更早起作用而取更小的值（例如 10 万）。这个值对所有组相同，定下后不再改。
6. **v0.2 打 tag 之前要先提交。** AdaMAS-unit 里补回 4855fb9 的改动还没提交（正对照 81/81）。建议提交后打 tag `v0.2`，再在其上开始 v0.3。提交、打 tag、推送都等同意。

## 8. 实现时定下的细节（需要时可改）

1. **阶段的 token 配额**：阶段开始时，取"剩余预算平均分给剩余阶段"，且不超过"剩余减去后续各阶段的保底"（保底为总预算的 5%）。配额用完时，程序关闭该阶段并进入下一阶段，代码保持原样；最后一个阶段用完则本轮结束。
2. **追加**：`request_budget share=<0..1>`（占可批上限的比例）或 `tokens=<N>`。可批上限 = 剩余 − 后续保底 − 本阶段还没用的部分；最后一个阶段没有可批的。批出的量不超过申请量。
3. **子智能体额度**：`budget=<0..1>`（占本阶段剩余的比例）或 `tokens=<N>`，必须给出。可批上限 = 本阶段剩余 − 执行者继续工作所需的余量（当前上下文加 4000）。
4. **次数上限的默认值**：审阅 4、修复 8、工作者 3、子智能体合计 10、压缩 8。读数里的 `repairs c/d` 就是修复者调用次数。
5. **记忆文件**：仓库根目录的 `AGENT_MEMORY.md`，被 git 忽略，不进最终代码。"在最近一次代码改动之后更新过"由程序按内容哈希判断。
6. **管理动作**：`stage_done`、`request_budget`、`subagent`、`compact`，以及只改记忆文件的命令，不计步数；步数上限默认执行者 400、子智能体 80，总调用数上限为 2 × 步数上限 + 24。
7. **执行者没有提交命令**：结束靠声明最后一个阶段完成。单执行者组声明后被提示继续，直到预算、步数或调用数用完。
8. **可提交的定义**：v0.3 没有冻结的验收套件，所以"可提交" = 包能导入、文档点名的名字可导入比例达到 v0.2 的阈值、文档里的命令行入口能运行。v0.2 里"验收套件能被收集"这一条不再适用。
9. **进展信号**：每 10 个计数步测一次（导入检查缺失数、执行者自己测试的通过数），在阶段结束时也测；耗时记为框架开销，不占预算。
10. **子智能体的读数**：格式相同，其中 `stage tokens` 一项对子智能体表示它自己额度的已用比例。
