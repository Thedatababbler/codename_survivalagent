## 1. 一句话

把一次完整的多阶段执行称为一个**轮回**：

- 仓库按冻结计划切成若干**单元**，单元之间只传代码，每个单元经过验收门，至多修复 3 次；
- 整个仓库共用一本**预算账本**，管 token、等待时间、上下文压缩次数、修复次数，由**预算规划者**分配和审批。

**进化的只有预算规划者。**它在轮回与轮回之间改进自己的资源安排，目标是：同一道题再做一次时，不耗尽预算，修复次数、步数、压缩次数都够用，最终代码一定能提交，并把纠错和时间花在更重要的单元上。

构建者、出题者、修复者在所有轮回中保持固定，也看不到任何上一轮回的信息。因此轮回之间的变化只能归因于预算安排。

本项目的 RSI 产出有两层：
- 规划者的经验，即预算表和通用规则；
- 经过验证后，从这些经验晋升而来的 harness 固定机制（§10）。

## 2. 为什么

来自 AdaMAS 多阶段版本（AdaMAS `docs/reports/hard_compare_20261023.md`，EXP-20261023-01）：

1. **开销大，提升小**：每次运行 21–41M prompt token，约为单个 Codex 会话的 34 倍，其中约 70% 花在修复候选上。各题平均 0.240 对 0.194；打开进化后为 0.195。
2. **子图和产物槽导致流水线缺陷**：产物槽冲突、记忆回执缺失导致整次运行崩溃、子图卡死。10 次运行中有 1–2 次因此报废。
3. **一个里程碑不过，后面全部阻塞**。

单元化（只传代码、没过门也继续）针对第 2、3 点；硬预算和固定修复次数针对第 1 点；可进化的规划者回答"预算该怎么花"。

## 3. 名词

| 名词 | 含义 |
|---|---|
| 仓库（repo） | 一道题。 |
| 单元（unit） | 一个阶段，来自冻结的里程碑计划（每题 4–5 个）。 |
| 轮回（round） | 用一个固定的预算策略，把一道题从空仓库完整跑完所有单元。第 k 轮回用策略 π_k。 |
| 预算策略 π | 每个单元的先验额度，加上运行中的审批规则。π_0 = 平均分配、不预留提交储备。 |
| 构建者 / 修复者 | 写代码、修代码的智能体，每个都是一个全新会话，跨轮回不保留任何东西。 |
| 出题者 | 按设计文档和单元验收条目写考卷的智能体。 |
| 冻结考卷 | 每个单元的考卷只出一次，之后所有轮回都重用，作为不变的尺子（§4.2）。 |
| 验收门 | 本单元考卷，加上之前所有单元的考卷，结果分三栏记录（§4.4）。 |
| 预算账本 | 一个轮回内整个仓库的预算记录。 |
| 预算规划者 | 轮回之内：分配额度、审批追加、决定是否修继承失败、提前收回额度。 |
| 预算进化者 | 轮回之间：读诊断，提出新的预算表和通用规则。 |
| 提交检查 | 机械检查最终代码能否交付，只观测、不行动（§7）。 |
| 单元重放 | 从某个单元开始时的代码快照出发，用不同额度重跑该单元，估计边际收益（§9.2）。 |

## 4. 一个轮回之内：单元流程

```
（轮回之前，只做一次）出题阶段：出题者为每个单元写考卷 → 冻结
                                                            │
第 k 轮回：                                                  ▼
输入代码（上一单元的输出；第一个单元为空仓库）
  │
  ├─ 构建者：在输入代码上实现本单元（额度来自规划者的先验分配）
  ├─ 验收门：本单元冻结考卷 + 之前所有单元的冻结考卷，结果分三栏
  │     第一栏、第三栏为空 → 本单元过门
  │     否则 → 修复（本单元至多 3 次；仓库至多 2 × 单元数次）
  │            第二栏要不要修，由规划者决定
  │     修复用完仍未过门 → 带着当前代码继续（继续模式）
  ▼
输出代码 → 下一单元 …… → 最终代码 → 提交检查（只观测）→ 轮回得分
```

### 4.1 输入与输出

- 输入：上一单元的输出代码（目录快照）和本单元说明（标题、目标、验收条目）。不传任何其他产物。
- 输出：代码快照，以及本单元记录（三栏门结果、修复次数、各项预算用量、规划者的决定）。
- 每个单元开始时的代码快照都要保存，单元重放（§9.2）要用。

### 4.2 出题与冻结考卷

- 出题者只看设计文档和单元验收条目，不看任何代码。因此可以**在所有轮回之前单独出题**，一次为全部单元写好考卷并冻结。
- 出题沿用 AdaMAS 的出题者，包括审计规则和修卷轮次，但关闭进化和记忆。
- 出题的花费记在单独的"出题账"上，**不计入任何轮回的预算 B**，否则只有出题的那一轮要付出题费，轮回之间就不可比。
- 但和对照组比较成本时，出题费用**要算进 AdaMAS-unit 的总成本**，并单独列出（§13.1）。单个 Codex 不需要出题，排除这笔费用会对 AdaMAS-unit 有利。
- 考卷在轮回之间不改。修复者对考卷的异议只记录，不在轮回之间修卷（D2）。

### 4.3 修复

- 每次修复是一个全新会话，输入是当前代码、门的失败证据和本单元说明。修复者自己读代码、跑考卷、改代码。
- 原地修改，不派生候选，不做选择。考卷对修复者只读。
- 上限取先到者：本单元 3 次，仓库 2 × 单元数次。具体上限可以由规划者在这个范围内收紧（§8.1）。

### 4.4 门结果三栏

继续模式下，前面没过门的单元，它的考卷会在后面每个门里反复失败。所以门的结果分三栏：

| 栏 | 内容 | 能否触发本单元修复 |
|---|---|---|
| 一 | 本单元新卷的失败 | 能 |
| 二 | 旧卷中继承来的失败：那个单元提交时就已失败 | 由规划者决定是否花钱修 |
| 三 | 旧卷中的新回归：那个单元提交时通过、现在失败 | 能 |

为此，每个单元提交时都要记下它的门在**每一条用例**上的结果，作为后续分栏的依据。

## 5. 预算

### 5.1 预算种类

总预算是一个向量 B = (token, 时间, 压缩次数, 修复次数)，按整个仓库计，记在一本账上。

| 预算 | 计量 | 谁消耗 | 何时检查 | 用完时 |
|---|---|---|---|---|
| 总 token | prompt token（含缓存），另记 completion | 构建者、修复者（规划者另记，见 §11） | 每次调用模型前 | 当前会话停止，余下单元只跑门 |
| 会话 token 额度 | 同上 | 单个会话 | 每次调用模型前 | 会话停止，停止前可以申请追加 |
| 总等待时间 | 墙钟秒数 | 所有会话和门 | 调用模型前；单条命令的超时 | 同"总 token" |
| 上下文窗口 | 会话当前上下文的 token 数 | 单个会话 | 调用模型前 | 触发一次压缩 |
| 压缩次数 | 次 | 全仓库共用一个池 | 压缩时 | 不能再压缩，会话在下一次超窗时停止 |
| 修复次数 | 次 | 修复者 | 门失败时 | 不再修复，继续模式 |

数值在 E0 校准（D4）。旧数据是 Codex 上的，只作参考。

### 5.2 先验分配

- 单元开始时，规划者按**本题预算表**（§8.1）给出该单元各项预算的份额。没有预算表时（π_0），平均分配：剩余 ÷ 剩余单元数。
- 用剩的额度回到账本。超支只能通过审批追加，所以前面单元花得多，后面单元自然就少。
- π_0 **不预留任何提交储备**，也不做任何收尾修复。是否预留、预留多少，由进化来学（D9）。

### 5.3 运行中的审批

- 智能体可以发出追加申请，写明要多少、哪一项预算、为什么。申请只是信号之一。
- 规划者依据**可核实的进展指标**做决定。这些指标全部由程序从账本和工作区算出，规划者看不到代码：
  - 门结果是否在改善；
  - 最近 N 步有没有代码变化（改动的行数和文件数）；
  - 本单元已用多少。
- 规划者还看本题预算表和已启用的通用规则。
- 规划者的决定有四类：批不批追加、批多少；第二栏的继承失败修不修；发现"无产出循环"时提前收回额度；在上限内收紧本单元的修复或压缩次数。
- **机械上限高于规划者**：账本先算出本次最多能批多少（剩余减去后面单元的保底额度），超出的部分自动截断。
- 每次申请和决定都写进账本。

### 5.4 截停与余量

- 检查只发生在两次模型调用之间。每次调用前留一个余量，剩余小于余量时，就当作已用完处理。
- 单条命令的超时不超过剩余时间。

### 5.5 总预算用完

- 正在运行的会话停止；余下单元不再调用智能体，只跑门做记录。
- 最终代码就是当时的代码，照常做提交检查和评分，并记录耗尽发生在哪个单元。

## 6. 上下文压缩

- 上下文超过窗口阈值时，保留系统提示、任务说明和最近若干轮，把较早的对话压成一段摘要。
- 每压缩一次就从池里扣一次，摘要调用的 token 也记入总账。
- 参考实现：本机 `/root/projects/Mini-Agent` 的 `_summarize_messages`。

## 7. 提交检查（只观测）

- 内容全部是机械检查，不调用模型：
  - 包能导入；
  - 文档点名的公开名称能导入；
  - 全部冻结考卷能收集（不要求通过）；
  - 如果文档写了命令行入口，入口能运行。
- 每个轮回结束时跑一次，结果记为 submittable ∈ {0, 1}。**不触发任何修复，也不占用任何预算。**基础版和所有对照组都用同样方式测量。
- 它是轮回得分的必含项，也是"耗尽导致不可提交"这项诊断的判据。
- 规划者和进化者都不能修改它的判据。
- 补丁 2026-11-09 起，提交检查在收尾导入修补（§7.1）之后执行，判据不变，仍只观测、只记录。

### 7.1 收尾导入检查与修补（补丁 2026-11-09，所有对照组相同）

- **为什么：** deepdiff 上 held out 反馈半比率的波动主要来自整个测试文件收集失败，原因是文档点名的名字导入不到（`docs/reports/heldout_variance_2026-11-09.md`）。这一步把"名字是否碰巧对上"的噪声对所有组同样去掉，不给任何组额外优势。
- **导入清单：** 由程序只从设计文档（数据集仓库的 `docs/`）推导，所有轮回开始前每道题生成一次并冻结（`outputs/importcheck/<task>/manifest.json`，记哈希），所有对照组共用。内容：
  - 写明模块的名字：文档里的 import 语句（含括号多行形式）、代码块里 `# in x.py` 段落、AdaMAS `public_symbols` 已归属的名字；
  - 没写模块的名字：文档 API 小节标题里的函数和类名；只记录，不检查、不修补（`unattributed: record`，用户决定 2026-11-09：其中混有 conftest fixture、nox 会话和 pytest 钩子，顶层检查会报出几十个缺失，超过修补上限）；
  - 排除测试与基准目录下的模块，以及 `test_*.py`、`*_test.py`、`conftest.py`；
  - 文档写明的命令行入口（`python -m <包>`、console script）。
- **检查：** 程序完成，不调模型；在沙盒内、在代码副本上运行。内容是清单中的名字能导入、包内各模块能导入、`__all__` 中的名字都存在、命令行入口能打印帮助。
  - AdaMAS-unit 在每个单元结束时检查一次（无论是否过门），只查模块归属于该单元及之前单元的名字。模块不属于任何单元或属于多个单元的（例如 `__init__.py`），以及没写模块的名字，只在最终提交前检查。
  - 单个会话对照组只在最终提交前检查一次。
- **修补：** 只在最终提交前，检查有问题时启动一次修补会话；两组都是一轮一次、额度相同（用户决定 2026-11-09；`importfix.*`：150,000 token、600 秒、150 行）。单元结束时的检查只记录缺失了哪些名字，不修补，作为诊断信息。
  - 记在它自己的账本上，不从轮回账本扣除，也不影响规划者和后续单元的额度；检查和修补的时钟时间记作 harness 开销。
  - 输入只有缺失名字列表、文档相关段落和代码。
  - 改动范围由程序检查：只能是导入、导出、`__all__`，以及缺失名字的新定义；不得改任何已有函数或类；改动不超过 `importfix.max_lines` 行。不满足就整体撤销，恢复修补前的代码。
  - 修补后重查一次，不做第二次修补。
- **记录：** `round.json` 的 `importcheck` 记录每次检查和修补的前后缺失数、修补用量，以及是否撤销。最终修补前的代码保存在 `final_before_importfix/`，用于报告修补前的反馈半比率。

## 8. 轮回之间：规划者的进化

### 8.1 规划者学什么、存在哪里

| 层 | 内容 | 适用范围 |
|---|---|---|
| 本题预算表 | 每个单元各项预算的份额，以及修复上限、压缩上限 | 同一道题的下一轮回 |
| 通用规则 | 从多道题总结出的规律，例如"整合单元至少留两成时间"；每条有试用、启用、淘汰三种状态 | 可用于新题；E1 期间只积累、不生效（D12） |
| 轮回摘要 | 每轮回一条记录：所用策略、各单元各项用量、诊断、轮回得分；不含任何代码 | 改进步骤的输入 |

这三层都存在规划者自己的状态目录里，构建者、出题者、修复者都读不到。

### 8.2 轮回隔离

| 跨轮回保留 | 跨轮回不得保留 |
|---|---|
| 规划者的预算表、通用规则、轮回摘要 | 上一轮回的代码和单元输出 |
| 冻结考卷 | 构建者和修复者的对话或经验 |
| 单元划分（冻结计划） | held out 的任何内容 |

### 8.3 轮回的结果指标与接受规则（D8，用户决定 2026-11-05）

不加权求和，不合成总分。每个轮回记录三项指标：
- submittable，看比例；
- 最终代码在**全部单元冻结考卷**上的通过率；
- 过门单元数，加上资源浪费（剩余未用、修复无效、无产出循环）。

> 补丁 2026-11-09：所有组的导入问题都由统一的收尾导入修补（§7.1）处理，submittable 对所有组会同时提高。因此它不再是进化要学会的主要贡献，改为记录项，同时作为"不变差"的守门项保留。预算进化的主要目标改为功能质量，即 held out 反馈半比率（E1 判定见补丁 2026-11-08）。补丁之后的基线和候选都必须在同一规则下重跑；补丁之前的轮回数据只作参考，不与之后的数据混合比较。

新策略要被接受，需要按优先级依次满足：

1. **submittable 的比例不低于现任策略**（首要）；
2. **冻结考卷的通过率提高，且超过噪声阈值 ε_noise**；
3. 前两项持平时，再看过门单元数是否增加、资源浪费是否减少。

报告时这几项分开列出。

收尾储备晋升进 harness（§10）之后，再考虑加上和储备有关的指标。
- 不用 held out 选择策略。反复做同一道题时，用 held out 选择就等于对着测试集调参。
- **E1 的进化完全不接触 held out**（反馈半也不用），只看冻结考卷和过程诊断。held out 按 AdaMAS 的做法对半拆分，评估半只在 E2 用来检验最终策略。
- 局限：冻结考卷是出题者自己出的，它和 held out 的关系在 AdaMAS 的实验里并不紧密。轮回得分上升只说明"同样预算下完成了更多文档写明的事"，是否转化为 held out 提升要在 E2 单独验证。

### 8.4 诊断（全部由程序从账本算出）

| 诊断 | 判定 | 提示 |
|---|---|---|
| 耗尽点 | 总预算在哪个单元耗尽 | 前面花太多，或这个单元太贵 |
| 进展中被截断 | 会话因额度停止时，最近一段门结果仍在改善 | 这个单元分少了 |
| 修复次数不够 | 3 次修复用满仍失败，但失败数单调下降 | 修复次数不够 |
| 修复无效 | 修复前后失败数不变 | 修复预算在浪费 |
| 剩余未用 | 单元结束时还剩大量额度 | 这个单元分多了 |
| 压缩后退化 | 压缩后门结果变差，或重做已完成的工作 | 压缩太早或太多 |
| 超窗停止 | 压缩次数用完后，会话因超窗停止 | 压缩次数太少 |
| 无产出循环 | 最近 N 步没有代码变化，门结果也没变 | 应该提前收回额度 |

"进展中""门结果改善"要在会话进行中也能看到。所以会话期间每 N 步做一次**进展测量**：
- 把工作区拷一份快照，在快照的副本上、在沙盒里跑本单元考卷，只记失败数。不在智能体正在工作的目录里测，免得测试留下缓存之类的文件，影响智能体的行为。
- 结果不告诉智能体。
- 测量所花的时间记为 **harness 开销**，不从智能体的等待时间预算里扣；报告总成本时照常计入。
- N 在 E0 定。

### 8.5 改进步骤

1. **诊断**（程序）：算出 §8.4 的全部诊断和本轮回的 submittable。
2. **提议**（一次模型调用，预算进化者）：读本题预算表、轮回摘要和诊断，提出新的预算表，同时可以提议 0–2 条通用规则。
3. **机械校验**：
   - 总和不超过 B；
   - 每个单元的份额不低于保底值；
   - 单次改动幅度有上限，建议每个单元的份额最多 ±30%（D10）。
4. **试用和接受**：下一轮回使用新表，按 §8.3 的优先级规则决定接受，否则回滚到现任策略。这和 AdaMAS"不低于现任才提交"是同一原则。

## 9. 噪声与单元重放

### 9.1 先测噪声

- E0 用同一个策略对同一道题跑 3 个轮回，得到 ε_noise。之后的接受都必须超过它。
- 旧数据显示波动很大，例如 imapclient 两次分别为 0.30 和 0.14。

### 9.2 单元重放

- 单元之间只传代码，所以每个单元开始时的快照就是天然的检查点。
- 要回答"给单元 k 多分 X 有没有用"，从单元 k 的快照出发，用不同额度各跑几次这个单元，比较本单元冻结考卷的结果即可。
- 重放的结果只用于估计边际收益，交给进化者参考，不写回任何轮回的结果。
- 重放的花费记在单独的"重放账"上，不计入轮回的预算 B，但计入实验的总额度。重放单独设上限，E1 之前向用户报预计用量。
- 如果要主张"进化后更省资源"，重放的消耗和进化者的调用都要算进**进化的总成本**，否则会低估进化本身的代价（§13.1）。

## 10. 晋升为 harness 机制

1. **候选**：一条通用规则在多道题、多个轮回中保持启用，而且带来可测的改进。例如"为收尾预留资源"让 submittable 从 x 升到 y，耗尽点后移。
2. **检验**：在 E3 的新题上，带这条规则和不带这条规则配对比较，改进仍然成立。
3. **晋升**：把它写成 harness 里的机械规则，harness 版本号加一，并记录来源轮回和证据。
4. **晋升后**：所有对照组仍以 π_0（没有这条机制）作为下限，同时报告"基础版 + 晋升机制"的结果，以说明这项能力来自进化，而不是先验设计。

## 11. 安全与隔离

- 规划者和进化者**不能**：
  - 改总预算 B；
  - 改考卷或门；
  - 改单元划分；
  - 改提交检查的判据；
  - 看到任何代码或 held out。

  它们只看账本、诊断和程序算出的指标。
- 它们的 token 单独记成"管理开销"，并设上限，例如不超过总预算的 2%。
- 沙盒规定、密封规定、"缺东西就报错停止"、每次报告都带沙盒越界警告，全部沿用 AdaMAS。
- 每个轮回使用独立的状态目录。停止进程只能按明确的进程号或进程组。

## 12. 明确不做的事

- 不做修复进化：没有修复记忆、候选搜索、诊断分类。
- 不做出题者进化：出题者版本固定，考卷冻结。
- 不用多智能体功能，每个会话就是一个智能体。

## 13. 实验计划

| 阶段 | 内容 | 回答的问题 |
|---|---|---|
| E0 | π_0 在同一道题上跑 3 个轮回；同一框架、同一预算下跑"单会话续跑"对照 | 轮回噪声有多大；单元化本身是否优于单会话 |
| E1 | 同一道题进化 5 个轮回，配合单元重放 | 规划者能否在做过的题上学会更好的安排：耗尽减少，得分提升超过噪声 |
| E2 | 用 held out 评估半验证 E1 的最终策略 | 内部得分的提升能否转化为 held out 提升 |
| E3 | 把启用的通用规则用在没做过的题上，只带规则、不带预算表 | 学到的是可迁移的规划能力，还是只是这道题的资源档案 |

- 第一批题从最近 5 道 hard 题（cerberus、autopep8、deepdiff、imapclient、python-hl7）中选 2 道做 E0–E1，其余留给 E3。
- **所有对照组都在新框架下重跑**（D7）。AdaMAS 的已有数据是 Codex 上的，只作背景参考，不直接拿来比较。
- E1 成功只说明"能为做过的题优化资源"；要说明规划能力本身在自我改进，需要 E3。
